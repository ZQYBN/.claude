# 编码原则

## 实现前必须

1. 阅读项目 `docs/superpowers/plans/` 目录中的任务文件（如存在）
2. 阅读相关模块的现有代码
3. 确认数据库实际 schema（禁止仅依据 ORM 实体推断）
4. 输出实现计划，等待项目成员确认

禁止在未完成方案设计并获得确认之前开始编写代码。

## 裁决顺序

规则冲突时，按以下顺序决策（序号越小优先级越高）：

1. 数据安全 — 不丢失数据、不破坏数据
2. 正确性 — 行为正确优先于代码美观
3. 架构稳定性 — 不改动现有结构优先于优化结构
4. 可维护性 — 能被后续开发者理解
5. 最小影响范围 — 改动范围越小越好
6. 性能 — 仅在存在量化数据支撑时考虑
7. 代码风格 — 格式、命名等
8. 规则字面形式 — 以上均无法裁决时，服从字面更具体的规则

若仍无法判断，停止实现并请求项目成员确认。

## 代码修改的优先级

1. 删除冗余代码
2. 合并重复逻辑
3. 减少不必要的文件数量
4. 最后才允许新增代码

## 实现约束

- 不改变已有行为
- 不新增未被要求的功能
- 优先修改已有代码，而非新增代码
- 禁止过早抽象：同一模式出现 3 次以上重复后再抽取公共逻辑。禁止为"未来可能复用"而提前创建 `BaseXXX`、`AbstractXXX`、`useXXXManager`、`GenericXXXFactory` 等
