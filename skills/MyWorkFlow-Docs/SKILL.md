# AI 文件处理工作流规范（Stage Pipeline Workflow v3.0）

非代码类文件处理阶段化流水线。面向长链路、多步骤、可迭代的文件任务，
以**文件系统状态**为唯一可信源，放弃"一步到位"模式。

整个工作流不依赖 AI 长期对话记忆，完全建立在 `./` 下的目录状态之上。

---

## 一、角色定位与核心宗旨

面对非代码类的长链路任务（文件处理、数据清洗、文档重构、报告生成、可视化图表等），
禁止一步到位，必须执行阶段化流水线。整个工作流不依赖 AI 长期对话记忆，
完全建立在文件系统状态这一唯一可信源之上。

---

## 二、核心铁律

- **禁止单次跨越：** 严禁合并阶段，严禁单次回复跨越多个生命周期，每个阶段必须独立交互。
- **物理只读隔离：** 原始输入目录及任意上一阶段的历史结果均为绝对只读，严禁覆写。
- **中间状态落盘：** 每个阶段的计算、清洗、转换结果必须生成对应的中间文件并落盘保存。
- **状态可回滚性：** 任何阶段发生错误，不得清空当前目录，必须保留现场以便进行断点恢复。
- **无 INIT 不启动：** 未经 Phase 0 初始化并获用户确认前，严禁进入任何处理阶段。

---

## 三、Phase 0: 初始化（INIT）

这是流水线的**门禁阶段**。未完成 INIT 并获用户确认前，AI 禁止输出任何处理结果、
禁止创建非目录文件、禁止进入 Phase 01。此阶段解决两个根本问题：**用哪个拓扑** 与 **文件在哪**。

### 3.1 意图识别与拓扑匹配

AI 收到任务后，第一步必须分析用户输入特征，在以下四套拓扑中**锁定其一**：

| 拓扑 | 匹配特征（关键词/场景） | 入口目录 |
|------|----------------------|---------|
| **通用处理** | CSV/Excel/JSON 清洗、格式转换、报表生成、数据可视化、图表 | `./00_input/` |
| **文档/论文生成** | 论文、报告、提案、文章、PPT 大纲、撰写、章节、审阅 | `./00_material/` |
| **RAG 知识库预处理** | RAG、知识库、向量、embedding、检索、chunking、语料 | `./00_raw_docs/` |
| **GIS 空间工程** | GIS、遥感、地图、投影、栅格、矢量、空间分析 | `./00_raw_data/` |

判定逻辑：
1. 扫描用户消息中的关键词
2. 命中特定领域关键词 → 使用对应衍生拓扑
3. 未命中任何衍生拓扑 → **默认使用通用拓扑**
4. 若用户任务跨领域（如"清洗 CSV 后写入知识库"），以**最终交付物形态**决定拓扑

### 3.2 虚拟创建声明

拓扑锁定后，AI 必须在对话中**显式输出完整的目录结构树**，声明这些目录已在 `./` 下就位：

```
============================================================
[当前活跃阶段]: Phase 0 INIT — 目录初始化
[选定拓扑]: 通用处理
[物理根路径]: ./
[当前运行状态]: 已声明，等待文件落盘确认
============================================================

已初始化目录结构：

./
├── 00_input/         # ← 请将原始文件放入此目录
├── 01_cleaning/
├── 02_transform/
├── 03_validate/
├── 04_analysis/
├── 05_visualization/
├── 06_output/
├── 90_temp/
├── 99_archive/
└── prompts/
```

### 3.3 根级 README.md 落盘

目录声明后，**立即**在 `./README.md` 写入任务元数据：

```markdown
# <任务名称>

## 任务目标
<一句话描述任务要达成什么>

## 拓扑选择
- 拓扑类型: <通用处理 / 文档论文 / RAG预处理 / GIS空间>
- 选择理由: <为什么匹配此拓扑>

## 输入文件
- <待用户确认后补充>
```

此文件是整个项目生命周期的元数据底座，后续所有阶段的 README 都通过 `../README.md` 回溯到它。

### 3.4 引导落盘与阻塞确认

AI 输出上述内容后，**必须**输出尾部阻塞协议：

```
------------------------------------------------------------
下一阶段预告: Phase 01 — <根据拓扑，如 01_cleaning 或 01_outline>
阻塞性确认:
1. 请将原始文件放入 [./00_input/]（或对应入口目录）
2. 确认文件就位后，回复"确认"以进入 Phase 01

在收到"确认"之前，AI 禁止进入任何处理阶段。
------------------------------------------------------------
```

### 3.5 INIT 阶段自检清单

AI 在 INIT 结束前必须确认：

- [ ] 拓扑已四选一锁定
- [ ] 目录结构已声明
- [ ] `./README.md` 已落盘
- [ ] 用户已被提示将文件放入入口目录
- [ ] 尾部阻塞协议已输出
- [ ] 用户已回复"确认"（或"文件已就位"）

**以上任一项未满足 → 停留在 Phase 0，禁止进入 Phase 01。**

## 五、阶段准入与 README 规范

每个阶段是一个独立的沙盒，未满足准入清单前，严禁推进。每完成一个阶段，
必须强制生成该阶段的处理结果文件与当前目录下的 `README.md`。

### README.md 模板：

```markdown
# Stage: [阶段名，如 02_transform]

## 输入来源
- ../01_cleaning/cleaned_v1.csv

## 处理算子与逻辑
1. [编码转换] 统一转换文件编码为 UTF-8，消除异常 BOM 头。
2. [时间清洗] 将非标时间字段统一转换为 ISO 8601 标准格式 (YYYY-MM-DD HH:mm:ss)。
3. [空值处理] 捕获空白字符串，统一映射为标准的 null 值。

## 输出明细
- ./normalized.json
```

## 六、版本命名与归档控制

- **递增版本控制：** 阶段性重要成果迭代必须使用明显的版本后缀（如 `report_v1.docx`，`report_v2.docx`）。
- **禁止含糊词汇：** 严禁出现 `final`，`new_final`，`real_final` 等混乱命名。
- **归档隔离机制：** 里程碑达成后，将旧版本顺移至 `99_archive/`，当前阶段目录仅保留最新活跃版本。

---

## 七、AI 强交互协议（Response Protocol）

每次对话响应（包括 Phase 0 INIT 和所有后续处理阶段），头部必须包含状态看板，尾部必须包含阻塞式确认。

### 7.1 头部状态看板

```
============================================================
[当前活跃阶段]: <Phase 0 INIT / 01_cleaning / 02_transform / ...>
[选定拓扑]: <通用处理 / 文档论文 / RAG预处理 / GIS空间>
[物理输入路径]: <上一阶段产出文件的相对路径>
[物理输出路径]: <当前阶段产出文件的相对路径>
[当前运行状态]: [进行中 / 已落盘待确认]
============================================================
```

- Phase 0 INIT 时 `[物理输入路径]` 写入口目录路径
- 处理阶段 `[选定拓扑]` 行可省略（INIT 已锁定）

### 7.2 尾部阻塞协议

```
------------------------------------------------------------
下一阶段预告: <下一阶段名称>
阻塞性确认:
请检查 [<当前阶段产出路径>] 是否符合预期。
回复"确认"将自动加载该文件并初始化下一阶段 [<下一阶段名称>] 的资产。
------------------------------------------------------------
```

**每阶段必须等待用户回复"确认"后方可推进。严禁抢跑。**

## 八、异常中断与错误恢复

当处理中断、代码报错或数据崩溃时，执行不回滚覆写原则：

1. **原地冻结：** 保持当前阶段目录状态，严禁为了重试而删除已有中间成果。
2. **日志落盘：** 将异常堆栈或错误描述写入 `90_temp/error_log.md`。
3. **暴露差量：** 向用户输出明确的失败根因分析，并提供针对当前断点的 Hotfix 方案，而非重头运行。

---

## 九、Prompts 资产管理

复杂任务的 Prompt 必须沉淀为可复用的组件，严禁硬编码。

- 统一存放于 `prompts/` 目录（如 `prompts/01_cleaning.md`）。
- 每个 Prompt 组件应具备三要素：
  - **输入契约（Inputs）：** 期望的输入文件格式与约束
  - **核心算子（Operators）：** 执行的转换/处理逻辑
  - **输出契约（Outputs）：** 产出的文件格式与保证

使其可审计、可重载。

---

## 十、判定界限：明确不适用场景

**软件工程/全栈代码开发：** 默认关闭此工作流。代码工程必须直接依托 Git 体系
（Branch, Commit, PR, Issue），由代码版本控制系统实现原生审计，避免造成目录冗余。

以下场景走 `MyWorkFlow`，不走本 skill：
- 功能开发、Bug 修复、代码重构
- API 接口开发、数据库 Schema 变更
- 前端组件/页面开发
- 任何涉及 `.java`、`.tsx`、`.ts`、`.py` 等代码文件的修改任务

以下场景走本 skill：
- CSV/Excel/JSON 数据清洗与格式转换
- 文档生成（报告、论文、提案、PPT 大纲）
- 数据可视化与图表生成
- 知识库/RAG 语料预处理
- GIS/遥感数据处理
- 任意多步骤文件转换流水线

---

## 十一、终极目标

通过构建面向 AI 文件任务的虚拟状态机，解决过程不可见、上下文断层及人工难以介入的沉淀痛点。
让每一次交付都具备完整的：

- **可追踪性（Traceability）：** Phase 0 有根 README，每个阶段有阶段 README，每步转换有记录
- **可复现性（Reproducibility）：** 输入不变 + 算子不变 → 输出不变
